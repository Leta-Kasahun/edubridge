## Competency-Based Assessment Engine

## 1. Reality Check — What EduBridge Actually Is

EduBridge is a **multi-tenant B2B SaaS platform for private educational institutions**.
It is **not** an LMS (no live sessions, SCORM, xAPI) and **not** an SIS (no registrar,
transcripts, official grading).

What it _is_:

| Capability | Phase 2 scope |
|---|---|
| Question authoring | Manual + upload-assisted (teacher-controlled) |
| Assessments | Digital, timed, teacher-assigned, auto + manual graded |
| Attempt engine | Browser-based, server-validated, idempotent |
| Learning evidence | Per-answer, per-topic, immutable append log |
| Mastery | Deterministic (accuracy-based), not ML |
| Student experience | Visual, card-based, progress-oriented — not spreadsheet rows |
| Multi-tenancy | Hard-partitioned by `tenantId` on every query, every response |

## 2. Enterprise Validation Principles (Non-Negotiable)

These apply to every endpoint, every service, every component in Phase 2.

### 2.1 Backend — Four Validation Layers

```
Request → [1] Zod Schema → [2] Business Rules → [3] Tenant Ownership → [4] DB Constraints
```

| Layer | What it enforces |
|---|---|
| **Zod schema** | Shape, type, required fields, string lengths, enum values |
| **Business rules** | Attempt limits, question compatibility, availability window, publish eligibility |
| **Tenant ownership** | Every `findFirst/findUnique` includes `tenantId` — missing = 404, not 403 |
| **DB constraints** | FK integrity, unique constraints, `Decimal` precision — last line of defence |

> [!IMPORTANT]
> **Never trust the client for score, correctness, or grading status.**
> `StudentAnswer.isCorrect`, `awardedPoints`, and `attemptScore` are computed
> server-side only, never accepted from the request body.

### 2.2 Idempotency Keys

| Operation | Idempotency guarantee |
|---|---|
| Attempt submission | Check `status !== IN_PROGRESS` before grading — re-submission returns existing result |
| Evidence creation | Append-only — never update, never deduplicate |
| Upload confirm | Check uploadId consumed flag before creating questions |
| Mastery recalculate | Upsert by `(studentId, topicId)` — safe to call multiple times |

### 2.3 Server-Side Time Enforcement

Attempt timer is enforced **server-side**:

1. `startedAt` is recorded at attempt creation (server timestamp).
2. On every answer autosave + on submit: if `now > startedAt + timeLimitMinutes`, mark attempt `EXPIRED` and reject save.
3. Client countdown is UX only — server is authoritative.

## 4. Feature-Proof Extension Points

Built correctly now so these require **zero refactoring later**:

| Future feature | Extension point today |
|---|---|
| AI question extraction (Phase 3) | Upload service step 3 is a replaceable `extractBlocks(file)` function — swap implementation only |
| LLM grading for SHORT_ANSWER | `ShortAnswerStrategy.grade()` returns `MANUAL_GRADING` status — future: call LLM, return `GRADED` |
| AI-generated questions | Questions enter `QuestionVersion` lifecycle at `DRAFT` — same review/publish flow |
| RAG-based AI Tutor | `LearningContent` already versioned and topic-linked — AI reads `PUBLISHED` versions |
| ML mastery (Phase 3) | `MasteryService.recalculate()` interface is stable — swap deterministic formula for ML model |
| Offline sync (Phase 3) | All attempt endpoints are idempotent — offline queue just replays requests |
| SMS notifications (Phase 3) | `LearningEvidence` + `MasteryHistory` are the data source — plug in SMS trigger |

**Key business rules in `question.service.ts`:**
- `createQuestion()` — validates `config` via `validateQuestionConfig()` before insert

**Key business rules in `attempt.service.ts`:**
- `startAttempt()` — checks `maxAttempts`, `availableFrom/Until`, student enrollment in section
- `saveAnswers()` — checks server-side time expiry before accepting
- `submitAttempt()` — idempotent: if already `SUBMITTED/GRADED`, return existing result
- After submit: calls `GradingEngine.gradeAttempt()` → `EvidenceService.createFromAttempt()` → `MasteryService.recalculateForAttempt()`
